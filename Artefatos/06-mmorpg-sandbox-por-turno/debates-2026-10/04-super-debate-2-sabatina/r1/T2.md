# T2: engine e arquitetura do cliente

## Especialidade: Unity no cliente, e um cliente "burro"

**Posição.** O cliente é Unity (LTS), e é fino: mostra o estado e anima eventos. Ele não decide nada e não roda o núcleo.

**Por que Unity e não Godot nem web (fatos):**
- **A arte já decidida só existe em Unity.** O debate de arte fechou com Synty Sidekick + Mixamo. A Synty diz que o Sidekick é "available for Unity only" e que não há prazo para outras engines ([Synty](https://syntystore.com/blogs/blog/introducing-sidekick-character-creator)). Trocar de engine é jogar fora a decisão de arte junto.
- **O Animator Humanoid** faz o retarget do Mixamo para qualquer corpo do Sidekick sem trabalho manual. Os "5 conjuntos de animação" votados cabem num só Animator Controller com camadas.
- **A Asset Store** tem prontos o contorno de 2 tons, a UI e o Steamworks.NET. Para quem tem 2h por noite, cada sistema comprado é uma semana a menos.
- **Custo:** o Unity Personal é grátis até US$ 200 mil de receita, a splash é opcional no Unity 6 e a Runtime Fee foi cancelada ([Unity](https://unity.com/pricing-updates)).

**Fraquezas dos outros (fato + opinião):**
- **Godot:** não tem Sidekick, a loja de assets é rasa e personagem modular com troca de peça em runtime fica por conta dele. O acervo mostra que a roupagem 10 (Go + Godot) montou um pipeline Blender→Godot e morreu antes de ter loop (`acervo/LINHA-DO-TEMPO.md`, linhas 58 e 168). O Godot C# ainda não exporta para web ([fórum Godot, abr/2026](https://forum.godotengine.org/t/is-there-an-update-on-exporting-c-projects-to-web/128821)), mas isso pouco importa num jogo só para PC.
- **Web (Three.js/Babylon):** não tem editor de cena, não tem máquina de estados de animação nem ferramenta de mapa. Ele construiria uma engine antes de construir o jogo. A roupagem do cliente web (MUD Moderno, mar/2026) e a do TS + Electron já morreram (`LINHA-DO-TEMPO.md`, linha 143).

**O custo honesto:** ele não sabe C#. A resposta é diminuir a área de C#, não trocar de engine. O cliente faz só isto:
1. Transforma o input em comando (clicou na casa, usou a skill X no alvo Y).
2. Mostra o movimento interpolando o caminho que o servidor validou.
3. Toca o **log de eventos da luta** numa fila, com a opção de acelerar ou pular.
4. Monta o personagem: o ID do item vira uma peça do Sidekick por uma tabela em `data/`.
5. Mostra a prévia que o servidor calculou (casas alcançáveis, % de acerto).

**O que o cliente não faz:** rolar dado, contar tempo, achar caminho com autoridade ou guardar estado que importe.

**Reconexão:** o cliente não guarda estado. Ao voltar, pede um snapshot e os eventos da luta a partir do último `seq`. Isso só é simples se a luta for log, e aí o cliente e o servidor reforçam um ao outro.

C# com TypeScript ao lado é perto o bastante: classes, async e generics. O cliente terá umas 2–3 mil linhas, não 30 mil.

## Outros pontos
- **Funcionamento:** o automático com o jogo aberto favorece o cliente leve. É preciso modo de janela minimizada, FPS baixo em segundo plano e som de alerta.
- **Servidor:** TS com WebSocket e Postgres, como o debate fechou. Não use framework MMO pronto, porque ele prende o modelo.
- **Paradigma:** núcleo funcional e puro (estado + comando → eventos); o cliente pode ser OO com MonoBehaviour, que é o idioma da Unity.
- **Monorepo:** `client/` com Git LFS só para os binários; o `data/` é compartilhado em JSON.
- **Contrato:** um JSON Schema único, do qual saem tipos TS e C# gerados. Não escreva o tipo duas vezes à mão.
- **Navegador:** não. Steam é o alvo e o Sidekick com texturas pesa; o WebGL da Unity existe, mas não é o foco.
- **Arte:** contorno por shader de pós-processamento no URP, não por malha duplicada.
- **Viabilidade:** é viável só se o primeiro cliente for uma cena com 1 personagem andando no grid e lutando contra 1 mob.
- **Steamworks:** o login pelo ticket da Steam (`GetAuthTicketForWebApi`) é validado no servidor. Não faça senha própria.
- **Abandono:** a regra "o cliente só troca se reprovar no teste do personagem modular" é a melhor trava que existe. Mantenha.

## Ataque: rede UDP/LiteNetLib "depois" (`docs/03-tecnico.md`)
Um jogo de turno com clique para andar e 20–30 jogadores por zona não precisa de UDP, nem agora nem depois. UDP obriga a escrever confiabilidade, ordem e reenvio, e esse é o trabalho que mais morde um dev solo. **No lugar:** WebSocket com JSON para sempre e MessagePack se a banda apertar. Isso tira uma fase inteira do roteiro.

Na mesma linha, a seta "Núcleo → Cliente" e o "pacote local no Unity" do mesmo doc contradizem o consenso de que o cliente não roda regra. Remova os dois.

## Defesa: combate em instância (decisão 3)
O ataque provável é que a bolha no lugar seria mais imersiva. Para o cliente, a instância é a escolha certa por 3 motivos:
- Quem passa não precisa receber animação de luta alheia, só um ícone parado. Isso é pouca banda e pouco código de sincronização.
- A luta carrega um recorte do terreno local, com o mesmo prefab do mapa e o grid por cima, sem cena nova para modelar.
- A reconexão cai num lugar só: entrar de novo na instância e tocar o log.

A bolha no mundo obrigaria a resolver oclusão, outros jogadores atravessando e câmera disputada.

## Ponto novo: o editor roda no PC dele?

O Unity Hub para Linux só sai oficialmente para Ubuntu e RHEL; no Arch vem pela AUR, sem suporte oficial (o caminho apareceu em `acervo/Conversas/Claude/2026-09-27_Instalando Unity no Garuda Moka.md`). - instalar o Unity 6 LTS;
- importar o Sidekick;
- fazer o build Linux e o Windows.

Se travar, a saída é dual boot ou uma partição Ubuntu, não trocar de engine.
